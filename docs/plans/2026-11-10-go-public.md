# M3: Going public — plan

> **For agentic workers:** use superpowers:subagent-driven-development for the PR tasks (part A). Every PR is reviewed by an agent other than its author. Part B are owner actions; the agent prepares exact steps but never flips visibility, creates releases, changes repo settings or deletes secrets itself.

**Goal:** both repos public, the app live on GitHub Pages, the app built from core release tarballs, GPL obligations met, nothing private leaked.

**Spec:** `docs/specs/2026-11-09-lily-on-eink-design.md` §3 (distribution, tarball decision), §10 (CI, branch protection, privacy, going-public checklist), §11 (M3).

**Decisions already taken:**
- Core is distributed as tarballs on GitHub Releases, not GitHub Packages and not (yet) npm (§3).
- Builds and publishing run only on **published releases**, never on tags alone.
- Lean CI: no privacy job in CI; privacy is checked locally and in this plan once over everything that turns public.

**Decisions confirmed by the owner (2026-11-10):**
1. First version: **0.1.0** for core, engine-wasm and the app.
2. App deploy trigger: **on a published app release**, plus manual `workflow_dispatch` with a tag input.
3. Pages URL: **`https://ranacrocando.github.io/lily-on-eink-app/`** (Vite `base` `/lily-on-eink-app/`, already the default). No custom domain.

**Open (owner, optional):** engine-wasm imports core only as a type. Making core a `peerDependency` of engine-wasm would remove the app's `overrides` entry. This deviates from spec §3; default: keep the spec as is.

## Part A — PRs prepared while the repos are still private

### A1 (core) Version 0.1.0 and release workflow
PR title: `ci: upload package tarballs to published releases`

- Bump `packages/core` and `packages/engine-wasm` to `0.1.0`, **and** engine-wasm's dependency `"@lily-on-eink/core"` to `0.1.0` (otherwise the workspace no longer satisfies it and `npm ci` goes to the registry). Regenerate `package-lock.json`.
- Add `description` and `repository` to both package.json files. Turn off source maps for the published build, or ship `src` (the maps point to `../src`, which is not in the tarball); pick the smaller change.
- `.github/workflows/release.yml`:
  - Triggers: `release: types: [published]` and `workflow_dispatch` with inputs `tag` (required) and `force` (boolean, default false).
  - Job `build` (`permissions: contents: read`): checkout at the release tag (dispatch: `ref: ${{ inputs.tag }}`, passed through `env:`, never interpolated into `run:`), setup Node like `ci.yml`, `npm ci`, `npm run build`, `npm test`; assert the tag `vX.Y.Z` equals both package versions and engine-wasm's core dependency; `npm pack -w packages/core -w packages/engine-wasm`; smoke install both tarballs into a clean temp project with the app's `overrides` entry and run one conversion of a corpus file; upload the `.tgz` as a workflow artifact.
  - Job `upload` (`needs: build`, `permissions: contents: write`, `GH_TOKEN` only in this step): download the artifact; on `release` and on dispatch without `force`, upload only assets that are missing; `--clobber` only with `force: true`. Reason: the app lockfile pins integrity hashes, and a rebuilt tarball can differ byte for byte.
- README (with A8): how to release (create the release in the UI on `main`; if the version check fails, delete release and tag, fix via PR, release again). Do not enable GitHub "immutable releases" (it blocks the upload after publishing).

### A3 (app) Version, corresponding source and Pages deploy
PR title: `ci: deploy the app to GitHub Pages on release with its source`

One workflow `.github/workflows/release.yml`, triggers `release: published` and `workflow_dispatch` (required `tag` input, via `env:`). Every run checks out the tag.

1. Job `source` (`permissions: contents: write`): build the corresponding source of the bundled engine (A4) and upload it to the release if missing. Runs on every app release, even when the engine is unchanged.
2. Job `deploy` (`needs: source`, so the site never goes live without its source; `permissions: pages: write, id-token: write, contents: read`; `environment: { name: github-pages, url: ${{ steps.deployment.outputs.page_url }} }`; `concurrency: { group: pages, cancel-in-progress: false }`): `npm ci`, build with `APP_BASE=/lily-on-eink-app/` and the tag injected as `VITE_APP_VERSION` (`import.meta.env`), `node scripts/check-build.mjs`, `actions/configure-pages`, `actions/upload-pages-artifact`, `actions/deploy-pages` (pinned like the others).

- Bump the app's `package.json` to `0.1.0`; the workflow asserts the tag equals it.
- About page: add a **Corresponding source** section (and a footer link) pointing to the source asset of the release the build came from (`VITE_APP_VERSION`), plus links to the exact source trees: `ranacrocando/lily-on-eink-app/tree/<tag>` and `ranacrocando/lily-on-eink/tree/v<core version>`.
- Notes: Pages serves `.wasm` as `application/wasm`; the ~31 MB engine is far below the limits; no COOP/COEP needed. Pages has a soft limit of ~100 GB/month bandwidth (roughly 3,000 cold visits); fine for now.

### A4 (app) Corresponding source bundle (GPLv3 §6(d))
Part of the A3 PR. The app conveys GPL object code (the LilyPond/Guile WASM build and the minified engine-wasm adapter) over the network, so it must give equivalent access to the corresponding source from the same place (§6(d)). No written offer (§6(b) targets physical products, lasts three years and needs a contact address).

`scripts/collect-engine-source.mjs` (runs **only in CI**; a local test run is never uploaded) builds `lily-on-eink-engine-source-<engine version>.tar`, version read from the installed engine:
- the engine package from the registry: `npm pack @sightread/lilypond-wasm@<version>` (no lifecycle scripts; do not pack `node_modules`, whose `prepack` needs bun), checked against the `integrity` in `package-lock.json`. It contains `build/build.sh`, `build/patches/*`, `build/stubs/*`, `build/sources.json`, `build/fetch-sources.mjs`, `DEVELOPMENT.md`, `licenses/`;
- every upstream archive in `build/sources.json` (16 entries), downloaded and verified against its SHA-256;
- **PCRE2 10.42**, which GLib pulls in through its Meson wrap and links into the WASM (URL and SHA-256 from `glib-<version>/subprojects/pcre2.wrap` inside the GLib archive);
- the font sources of the runtime data copied from a native LilyPond 2.26.0 install (`build.sh` `step_data`): Emmentaler is in the LilyPond archive; add a pinned upstream release archive of **URW Base35** (`ArtifexSoftware/urw-base35-fonts`, the version LilyPond 2.26.0 ships; AGPL-3.0 with font exception) and of **TeX Gyre** (GUST; for completeness). The fonts as shipped are inside the engine's `dist/runtime.data.bin`;
- `README-SOURCE.txt`: what this is; how to rebuild (`DEVELOPMENT.md`, host prerequisites, native LilyPond 2.26.0 as an input for the data step); the Emscripten/clang version as recorded in the `producers` section of `lilypond.wasm` (the toolchain itself is a general-purpose tool and not part of the corresponding source); links to the exact app and core source trees (tags).

Tar must be portable: `--owner=0 --group=0 --numeric-owner --mtime=@0` (or node-tar with `portable: true`), so no local user names, ids or times end up in it. Uncompressed (the parts are compressed already).

**Duty that follows (§6(d)):** never delete a release whose build was deployed, and never remove its source asset. Stated in the app README.

Tests: unit-test the hash check and the tar options; run the script once locally only to report the size, and delete the result.

### A5 (both repos) Privacy scan of everything that turns public
No PR if clean; findings are reported in chat, fixes as separate PRs.

What becomes public: all commits reachable from branches and tags, **all `refs/pull/*/head`** (kept forever, even after branch deletion), commits replaced by force-pushes (reachable by SHA from the PR timeline), PR titles, bodies and review comments, issues, release notes, Dependabot PRs, Actions run names and logs (logs to everyone, artifacts to signed-in users, while retained).

- Fetch `+refs/pull/*/head:refs/remotes/pr/*` in addition to all branches and tags; run the `privacy-check` logic over `git log --all -p` plus author/committer names and emails and commit messages.
- List force-push before-SHAs via `gh api repos/{owner}/{repo}/issues/{n}/timeline` (`head_ref_force_pushed`), fetch and scan those commits.
- Scan PR and issue texts and comments, release notes, and the Actions run list (names include PR titles and commit messages). Runners are GitHub-hosted, so log paths are `/home/runner/…`, not local paths.
- If anything is found in a commit that is reachable via `refs/pull/*` or a force-push: deleting branches does not help; the only remedies are GitHub Support or re-creating the repo. Decide with the owner before B3/B6.
- Lean option against old logs: delete old runs (`gh run list` / `gh run delete`) before going public, or accept them after the scan.
- Known state (2026-11-10): commits on both `main` branches are authored only by `ranacrocando <179312672+ranacrocando@users.noreply.github.com>` and Dependabot.
- Reviewed by a second agent with the denylist; the denylist itself never leaves the machine.

## Part B — owner actions, in this order

The agent prepares each step and checks the result afterwards.

1. **Merge A1–A6 and A8** (squash, any order; A7 stays a draft).
2. **Account and repo settings, both repos** (Settings → General):
   - Pull Requests: allow **squash merging only**; default commit message **"Pull request title"** (otherwise one-commit PRs use the commit message); enable **"Automatically delete head branches"**.
   - Account → Emails: "Keep my email addresses private" and "Block command line pushes that expose my email" are on.
3. **Last check:** the agent re-runs A5 on the final state of both repos; delete stale branches (and old Actions runs, if chosen).
4. **Core public:** Settings → General → Danger Zone → Change visibility → Public. Apply the ruleset (A2 command).
5. **Core release:** Releases → Draft a new release → tag `v0.1.0` on `main` → Publish. The release workflow uploads the two tarballs; the agent verifies them (download, checksum, smoke install).
6. **App switch:** the agent regenerates A7's lockfile against the published tarballs; mark ready; CI green without token; squash-merge.
7. **App public:** change visibility; apply the ruleset; Settings → Pages → Source "GitHub Actions"; then Settings → Environments → `github-pages` → Deployment branches and tags → **add tag rule `v*`** (by default only `main` may deploy, and the release run is on the tag).
8. **App release:** tag `v0.1.0` → Publish. The workflow attaches the corresponding source, then deploys Pages. The agent checks the live site: engine loads, a corpus file converts, About links and the source link work.
9. **Clean up secrets:** delete `CORE_REPO_TOKEN` (Actions **and** Dependabot secrets) and revoke the fine-grained token (GitHub → Settings → Developer settings).
10. **Afterwards:** bumping core in the app stays a manual PR that changes the tarball URLs.
